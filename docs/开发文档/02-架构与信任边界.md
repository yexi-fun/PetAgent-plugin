# 架构与信任边界

## 1. 两个仓库的职责

`PetAgent-plugin` 是插件作者和市场维护者的工作区，保存插件源码、运行时文件、manifest 模板、契约测试、市场索引和发布脚本。`PetAgent` 是宿主工程，保存 Cordis 装配根、插件管理器、sidecar 协议、native ABI、前端 URI 协议和 `pet-core` service seam。

外部插件不直接依赖宿主私有 Rust 类型。需要替换宿主能力时，遵守三件套：

1. 实现稳定的 `trait` 或线协议；
2. 使用约定的 service name（例如 `tools`、`llm`）；
3. 保持事件/消息协议和错误语义兼容。

## 2. 安装与启用生命周期

```text
市场索引 -> 下载 ZIP -> 解压路径检查 -> 解析 manifest
    -> 版本/目标/依赖/冲突检查 -> 入口文件检查
    -> 写入 plugins.lock（enabled=false）
    -> 启用 -> initialize/加载 -> health -> 注册工具或窗口
    -> 停用 -> 注销工具/关闭 worker/关闭窗口/卸载 DLL
```

frontend 窗口是独立 WebView session：启用时创建，用户主动关闭后插件仍保持 enabled，插件工具页可以重新打开同一窗口；停用、升级、卸载或宿主退出时，宿主先发送 `pet:plugin-frontend-dispose`，再关闭窗口。frontend 的 `pet-plugin://` RPC 只提供版本化 handshake、插件配置、窗口状态/关闭、通知和生命周期事件，不提供任意 `tauri.invoke`、Shell、文件系统或进程启动接口。

当前 `frontend` 与 `sidecar` 仍是两种独立插件类型；通用 `dependencies` 只用于安装、版本和启停依赖，不会自动建立 frontend 到 sidecar 的 RPC 通道。frontend + sidecar companion 属于后续 M6 协议，不能在 manifest 中通过普通依赖字段隐式启用。

安装器限制包大小（压缩包 100 MiB，解压包 300 MiB）、拒绝绝对路径、`..`、反斜杠和符号链接，并要求入口文件存在。`plugins.lock` 保存版本、路径、包 SHA-256、来源、健康状态和上一个版本。

## 3. 可信代码模型

插件不是沙箱脚本。MCP、sidecar、provider、native-dll 和 frontend 都在宿主用户的权限边界内运行：

- 不做 Ed25519、Authenticode 或 manifest 签名验证；
- 不把 `permissions` 转换成 ACL；
- sidecar 继承宿主环境变量，并额外收到 `PETAGENT_PLUGIN_ID`；
- native-dll 与宿主同进程，frontend 页面可执行其打包的 JavaScript；
- frontend 的 capability 白名单限制宿主 RPC 方法，但不限制页面自身 JavaScript、网络请求或第三方依赖；这不是浏览器沙箱；
- 市场固定仓库、人工审核、分支保护和 Release URL 是运营控制，不是运行时安全边界。

如果需要降低风险，应在插件自身设计最小行为、记录日志、提供可复现源码，并通过停用、卸载或回滚处理异常；不能把 manifest 权限声明当作安全承诺。

## 4. 宿主检查与安全边界的区别

| 检查 | 目的 | 是否提供沙箱 |
|---|---|---|
| SemVer、`petAgent`、`apiVersion` | 兼容性 | 否 |
| dependencies/conflicts | 装配一致性 | 否 |
| 相对路径、ZIP 穿越、符号链接 | 防止写出插件目录 | 否 |
| 包/解压大小 | 资源上限 | 否 |
| PE 架构、ABI 导出、init、health | 防止明显加载失败 | 否 |
| SHA-256 字段 | 完整性/展示元数据 | 否，当前不作信任决策 |
